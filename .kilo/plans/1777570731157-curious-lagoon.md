# 1. Abstract

PayFlow is an end-to-end, serverless, cloud-native anomaly detection pipeline built entirely on Amazon Web Services (AWS) that ingests payment transaction data, performs intelligent feature engineering, and flags potentially fraudulent transactions using unsupervised machine learning. The pipeline is designed to be source-agnostic — it accepts any payment dataset in CSV, Parquet, or JSON format and automatically detects column roles (transaction ID, amount, timestamp, card number, etc.) using keyword heuristics, eliminating the need for hardcoded schemas. Raw data is uploaded either via the AWS CLI or through a web portal featuring drag-and-drop uploads powered by presigned S3 URLs. An EventBridge rule triggers an AWS Glue PySpark ETL job on upload, which deduplicates records, masks sensitive card numbers, engineers transaction features (velocity, amount deviation, geo-flag, hour risk, etc.), and writes partitioned Parquet to a clean S3 zone. Glue Crawlers auto-catalog the data into a Glue Data Catalog governed by Lake Formation. A Lambda function running an Isolation Forest model inside a container image (stored in ECR) reads the schema metadata, dynamically constructs the feature matrix, trains the model with 2% contamination, and scores all transactions — outputting scored Parquet files, a top-1000 anomalies CSV, and a summary JSON. Results are accessible via Athena SQL queries, a QuickSight dashboard, and a real-time web portal served through CloudFront. The entire pipeline is orchestrated via EventBridge and Lambda intermediary functions, provisioned as Infrastructure as Code using Terraform, and validated through GitHub Actions CI/CD. Processing 590,540 transactions, the pipeline flagged 11,807 anomalies at a 2.00% detection rate, with a total weekly operating cost of approximately $1.13 — demonstrating that production-grade fraud detection can be achieved on AWS at near-zero cost within the free tier.

# 2. Introduction

## 2.1 Problem Statement

The rapid growth of digital payment systems has created an urgent need for automated, scalable fraud detection mechanisms. Traditional rule-based approaches require constant manual updates and fail to capture emerging fraud patterns. Machine learning–based anomaly detection offers a data-driven alternative, but deploying such systems at scale presents significant engineering challenges: data ingestion pipelines must handle varying formats and schemas, feature engineering must be robust across diverse datasets, and the inference infrastructure must be cost-effective for both batch and near-real-time workloads. Furthermore, in real-world scenarios, labeled fraud data is often unavailable, making unsupervised approaches essential.

## 2.2 Objectives

The primary objectives of the PayFlow project are:

1. **Build a fully serverless, cloud-native ETL and ML pipeline** on AWS that processes payment transaction data end-to-end — from raw ingestion through anomaly detection and visualization — without provisioning any long-running servers.

2. **Design a source-agnostic pipeline** that automatically detects column roles (transaction ID, amount, timestamp, card number, etc.) from any CSV, Parquet, or JSON dataset, eliminating hardcoded schema dependencies and enabling reuse across diverse payment datasets.

3. **Implement unsupervised anomaly detection** using Isolation Forest, an algorithm well-suited for fraud detection where labeled data is scarce, deployed as a containerized Lambda function for cost-effective, on-demand scoring.

4. **Establish data governance and security** through AWS Lake Formation for fine-grained access control, least-privilege IAM policies, credit card masking in the ETL layer, S3 versioning and public access blocks, and Athena query cost limits.

5. **Provide real-time pipeline visibility** through a web portal with drag-and-drop upload, live pipeline status tracking, and instant anomaly results — powered by API Gateway and Lambda backend functions.

6. **Minimize operational cost** by leveraging AWS free-tier services and serverless architectures, achieving a total weekly cost of approximately $1.13.

## 2.3 Scope

The PayFlow pipeline covers the complete lifecycle of payment fraud detection:

- **Data Ingestion:** Browser-based drag-and-drop upload or CLI upload to S3, with automatic pipeline triggering via EventBridge.
- **ETL Processing:** AWS Glue PySpark job that auto-discovers data files, infers column roles, performs deduplication, card masking, feature engineering, and partitioned Parquet output.
- **Data Cataloging & Governance:** Glue Crawlers for automatic schema discovery, Lake Formation for database-level access control, and Athena workgroups with scan limits for cost protection.
- **Machine Learning:** Lambda Container Image running Isolation Forest with dynamic feature matrix construction based on schema metadata.
- **Alerting & Notification:** SNS email alerts with detection summaries, SQS dead-letter queue for error handling.
- **Visualization & Access:** QuickSight dashboard for business users, web portal for interactive upload and results viewing, Athena for ad-hoc SQL queries.
- **Infrastructure as Code:** Complete provisioning via Terraform with 10 modules, CI/CD via GitHub Actions.
- **API Layer:** HTTP API Gateway with three routes (upload URL generation, pipeline status, results retrieval) for frontend-backend communication.

## 2.4 Technology Rationale

The choice of AWS serverless services is deliberate:

- **Glue PySpark** handles large-scale data transformation (590K+ records, 394 columns) with auto-scaling workers, eliminating cluster management overhead.
- **Lambda Container Images** allow packaging ML libraries (scikit-learn, pandas, numpy) that exceed the 250MB zip deployment limit, while still benefiting from serverless pay-per-invocation pricing.
- **EventBridge** provides native event-driven orchestration between S3, Glue, and Lambda without custom scheduling logic.
- **Lake Formation** adds enterprise-grade governance without additional cost.
- **Terraform** ensures reproducible, auditable infrastructure with state locking via DynamoDB.

## 2.5 Dataset

The pipeline was tested with the IEEE-CIS Fraud Detection dataset from Kaggle, containing 590,540 transaction records with 394 features including TransactionID, TransactionAmt, TransactionDT, card1–card6, addr1, addr2, ProductCD, and numerous anonymized V/M/C/D features. The dataset has a known fraud rate of approximately 3.5%, making it ideal for testing a 2% contamination-based anomaly detector. Critically, the pipeline is not limited to this dataset — the auto-detection engine in `schema_utils.py` enables it to process any payment transaction dataset with at least a transaction ID and amount column.

## 3.4 AWS Glue — ETL Pipeline

### 3.4.1 Glue Database and Job Configuration

**Screenshot:** AWS Console → Glue → Data Catalog → Databases showing `payflow_db`. Also, AWS Console → Glue → ETL Jobs showing `payflow-etl-job` with Glue version 4.0, worker type G.1X, 2 workers, timeout 30 minutes.

**Description:** A Glue Catalog database `payflow_db` is created to hold all tables discovered by crawlers. The ETL job `payflow-etl-job` is configured with Glue version 4.0 (latest), 2 G.1X workers (each with 1 vCPU and 16GB memory), and a 30-minute timeout. The job's script location points to `s3://payflow-glue-scripts-dev-104573823385/glue_etl_job.py`. Default arguments pass the raw and clean bucket names along with the optional `SOURCE_CONFIG` override. The job language is Python 3.

### 3.4.2 Glue ETL Script — Auto-Discovery

**Screenshot:** Code editor showing the first section of `glue_etl_job.py` — the boto3-based S3 file discovery logic that uses `list_objects_v2` with pagination to find all CSV, Parquet, and JSON files in the raw bucket.

**Description:** The Glue ETL script begins by discovering data files in the raw bucket using boto3's S3 paginator rather than Hadoop's FileSystem API. This was a critical fix — the original Hadoop `FileSystem.listStatus()` approach failed in Glue 4.0 with the error "Wrong FS: s3://, expected: file:///". The boto3 approach works reliably and supports pagination for buckets with many files. The first discovered file is selected, and its extension determines the read format (CSV with header inference, Parquet, or JSON with multiline support).

### 3.4.3 Glue ETL Script — Column Role Detection

**Screenshot:** Code editor showing the `find_by_keywords` function and the column role inference logic in `glue_etl_job.py` — matching column names against keyword lists for transaction_id, amount, timestamp, card_number, address, and product_code.

**Description:** The column role detection engine is the core of the source-agnostic design. For each canonical role (transaction_id, amount, timestamp, card_number, address_1, address_2, product_code), the engine first checks if an override mapping was provided, then searches for columns matching keyword patterns. For example, the amount role searches for columns containing 'amt', 'amount', 'price', 'total', 'value', or 'sum'. If no keyword match is found, statistical heuristics provide fallback: for amount, the first numeric column with >90% positive values; for transaction_id, the first column with all unique values. This enables the pipeline to work with any dataset that has at least a transaction ID and amount column.

### 3.4.4 Glue ETL Script — Feature Engineering

**Screenshot:** Code editor showing the conditional feature engineering section of `glue_etl_job.py` — deduplication, card masking, transaction hour extraction, amount bucketing, velocity computation, merchant average, amount deviation, and geo flag creation.

**Description:** Feature engineering is conditional based on detected column roles. Each feature is computed only if its prerequisite source columns are available:

- **Deduplication** by `transaction_id` (if detected)
- **Card masking** — masks credit card numbers to `****-****-****-XXXX` format (if card_number detected)
- **Transaction hour** and **is_weekend** — extracted from numeric timestamps or parsed datetime strings (if timestamp detected)
- **Amount bucket** — categorizes amounts as low (<50), medium (50-500), high (>500) (always computed if amount exists)
- **Transaction velocity** — count of transactions per hour using window functions (if transaction_id + timestamp detected)
- **Merchant average amount** and **amount deviation** — per-product-code statistics using window functions (if product_code + amount detected)
- **Geo flag** — flags transactions where address_1 != address_2 (if both address columns detected)

This conditional approach ensures the pipeline never fails due to missing optional columns — it simply skips features that aren't computable.

### 3.4.5 Glue ETL Script — Schema Metadata Output

**Screenshot:** Code editor showing the `_schema.json` writing section using `s3_client.put_object()` with the JSON schema_info containing source_file, source_format, column_roles, renamed_columns, detected_features, partition_columns, and record_count.

**Description:** After the ETL completes, the job writes a `_schema.json` metadata file to the clean bucket. This file captures the detected column roles, rename mappings, list of engineered features, partition columns, and record count. Downstream consumers — particularly the anomaly detection Lambda — read this schema to determine which columns and features are available, enabling dynamic feature matrix construction without hardcoded column names. The original approach using Spark's `saveAsTextFile()` failed in Glue 4.0 with `ClassNotFoundException: DirectOutputCommitter`, so boto3 `put_object()` is used instead.

### 3.4.6 Glue ETL Job Run

**Screenshot:** AWS Console → Glue → ETL Jobs → History tab for `payflow-etl-job` showing a successful run with status SUCCEEDED, duration ~5 minutes, 2 G.1X workers, and the CloudWatch Logs link.

**Description:** The Glue ETL job processes the 590K-record dataset in approximately 5 minutes using 2 G.1X workers. The job reads the raw CSV, infers column roles, performs all conditional feature engineering, and writes partitioned Parquet files to `s3://payflow-clean-transactions-dev-104573823385/clean/`. The partitioning scheme (year/month/region) enables partition pruning in Athena queries. The CloudWatch Logs show the auto-detected format (CSV), detected column roles, raw record count (590,540), and clean record count after deduplication and filtering.

### 3.4.7 Glue Crawlers

**Screenshot:** AWS Console → Glue → Crawlers showing two crawlers: `payflow-clean-crawler` (data store: clean bucket S3 path) and `payflow-scored-crawler` (data store: scored bucket S3 path), both pointing to database `payflow_db`.

## 3.6 Amazon Athena — SQL Query Engine

### 3.6.1 Athena Workgroup Configuration

**Screenshot:** AWS Console → Athena → Workgroups showing `payflow-workgroup` with bytes scanned cutoff per query set to 1,073,741,824 (1 GB), and output location `s3://payflow-athena-results-dev-104573823385/`.

**Description:** A dedicated Athena workgroup `payflow-workgroup` is created with a 1 GB per-query scan limit. This cost protection measure prevents runaway queries from scanning terabytes of data and incurring large charges. The workgroup's output location is set to the athena-results S3 bucket. All queries are run through this workgroup to enforce the scan limit.

### 3.6.2 Athena Query — Daily Transaction Volume

**Screenshot:** Athena query editor showing the `daily_volume.sql` query execution: `SELECT year, month, day, COUNT(*) AS txn_count, ROUND(SUM(amount), 2) AS total_amount, ROUND(AVG(amount), 2) AS avg_amount FROM payflow_db.payflow_clean_transactions_dev_104573823385 GROUP BY year, month, day ORDER BY year, month, day;` with results showing daily transaction counts and amounts.

**Description:** The daily volume query aggregates transactions by date partition, providing a time-series view of payment activity. Running on Parquet-partitioned data with partition pruning, Athena only scans the relevant partitions rather than the entire dataset, reducing both cost and query time. The query completes in seconds and returns row counts and aggregate amounts per day.

### 3.6.3 Athena Query — Fraud Merchants

**Screenshot:** Athena query editor showing the `fraud_merchants.sql` query: `SELECT ProductCD AS merchant_category, COUNT(*) AS suspicious_txns, ROUND(SUM(amount), 2) AS total_suspicious_amount, ROUND(AVG(amount_deviation), 4) AS avg_deviation FROM payflow_db.payflow_clean_transactions_dev_104573823385 WHERE geo_flag = 1 AND amount_bucket = 'high' GROUP BY ProductCD ORDER BY suspicious_txns DESC LIMIT 20;` with results showing merchant categories ranked by suspicious transaction count.

**Description:** The fraud merchants query identifies product categories with the most high-risk transactions (geo_flagged + high amount). The `amount_deviation` column (engineered by the ETL) shows how far each category's transaction amounts deviate from the category average — a strong indicator of anomalous behavior. This query demonstrates the value of feature engineering: without the pre-computed geo_flag and amount_bucket columns, this analysis would require complex window functions.

### 3.6.4 Athena Query — Peak Transaction Hours

**Screenshot:** Athena query editor showing the `peak_hours.sql` query: `SELECT transaction_hour, COUNT(*) AS txn_volume, ROUND(AVG(amount), 2) AS avg_amount, SUM(geo_flag) AS geo_flagged_count FROM payflow_db.payflow_clean_transactions_dev_104573823385 GROUP BY transaction_hour ORDER BY transaction_hour;` with results showing a 24-hour distribution of transaction volumes.

**Description:** The peak hours query reveals the hourly distribution of transactions and the concentration of geo-flagged anomalies. This analysis identifies high-risk time windows — for example, transactions between 11 PM and 4 AM may show disproportionately high fraud rates. The `transaction_hour` feature was extracted from the raw timestamp by the ETL, making this query simple to write and fast to execute.

### 3.6.5 Athena Query — Settlement Report

**Screenshot:** Athena query editor showing the `settlement_report.sql` query: `SELECT ProductCD AS merchant_category, COUNT(*) AS total_txns, ROUND(SUM(amount), 2) AS settlement_amount, ROUND(AVG(amount), 2) AS avg_txn_value FROM payflow_db.payflow_clean_transactions_dev_104573823385 WHERE isFraud = 0 GROUP BY ProductCD ORDER BY settlement_amount DESC;` with results showing settlement amounts by category.

**Description:** The settlement report provides a business-oriented view, aggregating non-fraudulent transactions by product category for settlement processing. This query is useful for finance teams to reconcile daily settlement amounts. Running on columnar Parquet format with partition pruning, it scans significantly less data than an equivalent query on raw CSV.

### 3.7.3 ECR Build and Push Process

**Screenshot:** Terminal showing the ECR login command, repository creation, docker buildx build with `--platform linux/amd64 --provenance=false`, and push to `104573823385.dkr.ecr.ap-south-1.amazonaws.com/payflow-anomaly-detector:latest`.

**Description:** The container image is built and pushed in a single `docker buildx build` command. Authentication to ECR uses the `get-login-password` pipeline. The `--platform linux/amd64` flag ensures compatibility with Lambda's x86_64 architecture (critical — building on ARM Mac produces incompatible images). The `--provenance=false` flag was a hard-won discovery: without it, Docker creates a multi-attestation manifest that Lambda cannot parse, resulting in "Image manifest does not contain descriptor for linux/amd64" errors.

### 3.7.4 Lambda Anomaly Detection Script — Schema Reading

**Screenshot:** Code editor showing the `_read_schema` function in `anomaly_lambda.py` that reads `_schema.json` from the clean bucket (trying both `clean/_schema.json/part-00000` and `clean/_schema.json` paths) and the `_build_column_list` function that extracts columns from the schema.

**Description:** The Lambda reads the schema metadata written by the Glue ETL job to determine which columns are available. Two S3 key paths are tried because Spark's `saveAsTextFile()` writes output as a directory with part files, while `boto3 put_object()` writes a single file. The `_build_column_list` function constructs the list of columns to project from Parquet, combining detected source columns, engineered features, and partition columns.

### 3.7.5 Lambda Anomaly Detection Script — Dynamic Feature Matrix

**Screenshot:** Code editor showing the `_build_features` function in `anomaly_lambda.py` that conditionally constructs features (txn_velocity, amount_z_score, geo_jump_score, hour_risk_score, amount_bucket_enc, is_weekend) based on which columns are available in the DataFrame.

**Description:** The dynamic feature matrix builder is the Lambda-side counterpart of the ETL's conditional feature engineering. It reads the DataFrame and schema, then constructs features only from columns that are present. For example, `txn_velocity` is used if available, `amount_z_score` requires both amount and merchant_avg_amount, and `hour_risk_score` applies a 1.5x multiplier for late-night hours (11 PM – 4 AM). If fewer than 2 features can be constructed, a fallback `amount_z_fallback` is computed from the amount column alone. This ensures the Lambda never crashes on an unfamiliar dataset.

### 3.7.6 Lambda Anomaly Detection Script — Isolation Forest Training

**Screenshot:** Code editor showing the model training section: `StandardScaler().fit_transform(features)`, `IsolationForest(n_estimators=100, contamination=0.02, random_state=42, n_jobs=1)`, model.fit(X), decision_function scoring, and anomaly_score computation (0-100 scale).

**Description:** The Isolation Forest model is trained with 100 estimators and a contamination rate of 0.02 (matching the ~2% expected fraud rate). Features are standardized using StandardScaler before training. The `n_jobs=1` parameter is critical because Lambda provides a single vCPU — using more would cause context switching overhead. The decision function's raw scores are normalized to a 0-100 scale where 100 indicates the highest anomaly. The `is_anomaly` binary label (0/1) is derived from the model's predict method (-1 = anomaly).

### 3.7.7 Lambda Anomaly Detection Script — Partitioned Scored Output

**Screenshot:** Code editor showing the scored data writing loop: iterating over groupby(year, month, region), writing each partition as a separate Parquet file to `scored/year=X/month=Y/region=Z/scored.parquet` via `s3.put_object()`.

**Description:** Scored data is written back to S3 in Hive-compatible partitioned format, matching the same year/month/region scheme as the clean data. This enables partition pruning in Athena queries on the scored table. The data is written partition-by-partition using `s3.put_object()` with BytesIO buffers, keeping memory usage controlled. After writing all partitions, the top 1000 most anomalous transactions are extracted and saved as `top_anomalies.csv`, and a `_summary.json` file is written with detection statistics for the frontend API.

## 3.8 Amazon EventBridge — Pipeline Orchestration

### 3.8.1 EventBridge Rule — S3 Upload Trigger

**Screenshot:** AWS Console → EventBridge → Rules showing `payflow-s3-upload-trigger` with event pattern: source `aws.s3`, detail-type `Object Created`, detail.bucket.name `payflow-raw-transactions-dev-104573823385`, target `payflow-glue-trigger` Lambda.

**Description:** The first EventBridge rule listens for S3 `Object Created` events from the raw transactions bucket. When a file is uploaded (via CLI or browser), EventBridge invokes the `payflow-glue-trigger` Lambda function, which in turn calls `glue:start_job_run()` to start the ETL job. EventBridge cannot directly target Glue jobs — it returns a 400 error — so the Lambda intermediary function is necessary. This pattern (EventBridge → Lambda → Glue) was a significant architectural discovery.

### 3.8.2 EventBridge Rule — Glue Success Trigger

**Screenshot:** AWS Console → EventBridge → Rules showing `payflow-glue-success-trigger` with event pattern: source `aws.glue`, detail-type `Glue Job Run Status`, detail.jobName `payflow-etl-job`, detail.state `SUCCEEDED`, target `payflow-crawler-trigger` Lambda.

**Description:** The second EventBridge rule listens for Glue job completion events. When the ETL job reaches SUCCEEDED state, EventBridge invokes the `payflow-crawler-trigger` Lambda function, which starts both crawlers (clean and scored). The crawler trigger Lambda handles `AlreadyRunningException` gracefully — if a crawler is already running, it logs the condition and continues. This chained orchestration (S3 → Glue → Crawlers) creates a fully automated pipeline triggered by data upload.

### 3.8.3 Lambda Intermediary — Glue Trigger Function

**Screenshot:** Code editor showing the inline Lambda function in `eventbridge/main.tf` using a Terraform heredoc: `glue = boto3.client('glue')`, `JOB_NAME = 'payflow-etl-job'`, and `glue.start_job_run(JobName=JOB_NAME)`.

**Description:** The glue trigger Lambda is a minimal function (8 lines of Python) deployed as an inline zip within the Terraform configuration using `data.archive_file`. Its sole purpose is to receive the EventBridge event and call `glue.start_job_run()`. This intermediary pattern was necessitated by EventBridge's inability to target Glue jobs directly. The function has its own IAM role with scoped `glue:StartJobRun` permission limited to the specific job ARN.

### 3.8.4 Lambda Intermediary — Crawler Trigger Function

**Screenshot:** Code editor showing the inline Lambda function: iterating over crawler names (`payflow-clean-crawler`, `payflow-scored-crawler`), calling `glue.start_crawler(Name=crawler_name)` with exception handling for `AlreadyRunningException`.

**Description:** The crawler trigger Lambda starts both crawlers sequentially. It handles the case where a crawler is already running (returning an `AlreadyRunningException`) by logging and continuing. The function has `glue:StartCrawler` permissions scoped to the two specific crawler ARNs. Like the glue trigger, this function is deployed as an inline zip within Terraform, avoiding the need for separate code files.

## 3.10 API Lambda Functions

### 3.10.1 Presigned URL Lambda

**Screenshot:** Code editor showing `presigned_url_lambda.py` — validating file extension, generating `s3.generate_presigned_url('put_object', ...)` with 300-second expiry, and returning the URL with CORS headers.

**Description:** The presigned URL Lambda generates time-limited S3 upload URLs for the frontend. It validates that the requested file extension is one of the allowed types (.csv, .parquet, .json), then generates a presigned PUT URL pointing to the raw transactions bucket. The 5-minute expiry balances security (the URL is short-lived) with usability (gives the user time to upload large files). All responses include CORS headers to support browser requests from the CloudFront domain.

### 3.10.2 Pipeline Status Lambda

**Screenshot:** Code editor showing `pipeline_status_lambda.py` — checking raw bucket for files, Glue job runs for ETL status, crawler state for cataloging status, and scored bucket for _summary.json existence.

**Description:** The status Lambda implements a 4-stage pipeline health check. Stage 1 checks if the raw bucket has any objects (upload complete). Stage 2 queries the latest Glue job run state (SUCCEEDED/RUNNING/FAILED/STARTING). Stage 3 checks the clean crawler's state (READY/RUNNING) and its LastCrawl status. Stage 4 checks for `_summary.json` in the scored bucket (anomaly detection complete) or falls back to checking for scored Parquet files (running). The function uses the `REGION` environment variable (not `AWS_REGION`) and returns CORS-compliant responses.

### 3.10.3 Results Lambda

**Screenshot:** Code editor showing `results_lambda.py` — reading _summary.json, parsing top_anomalies.csv as DictReader, and optionally redirecting to a presigned download URL.

**Description:** The results Lambda serves dual purposes: it returns anomaly detection results as JSON for the frontend display, and provides a CSV download via presigned URL redirect. The summary includes total_scored, anomalies_detected, anomaly_rate_pct, source_file, and features_used. The top anomalies are limited to 100 rows for API response size. When `download=true` is requested, a 302 redirect to a presigned S3 URL allows the browser to download the full 1000-row CSV directly from S3.

### 3.10.4 API Lambda IAM Policies

**Screenshot:** IAM → Role `payflow-api-lambda-role` → Permissions showing three scoped inline policies: presigned-s3-policy (s3:PutObject on raw bucket only), status-glue-policy (glue:GetJobRuns, glue:GetCrawler, s3:ListBucket on raw + scored), results-s3-policy (s3:GetObject on scored bucket only).

**Description:** Each API Lambda function has a scoped inline policy granting only the permissions it needs. The presigned URL Lambda can only `PutObject` to the raw bucket. The status Lambda can only read Glue job/crawler metadata and list (not read) the raw and scored buckets. The results Lambda can only `GetObject` from the scored bucket. No function has delete, update, or cross-bucket access. This least-privilege approach limits the blast radius of any compromised function.

## 3.15 End-to-End Pipeline Execution

### 3.15.1 Complete Data Flow Walkthrough

**Screenshot:** Diagram showing the complete data flow: Raw CSV → S3 Raw → EventBridge → Glue Trigger Lambda → Glue ETL → S3 Clean → EventBridge → Crawler Trigger Lambda → Glue Crawlers → Data Catalog → Lambda ML → S3 Scored → Web Portal + Athena + QuickSight + SNS.

**Description:** The complete pipeline flows through 8 stages: (1) User uploads CSV/Parquet/JSON to raw S3 bucket via CLI or web portal. (2) S3 ObjectCreated event triggers EventBridge Rule 1. (3) EventBridge invokes glue-trigger Lambda which starts the Glue ETL job. (4) Glue ETL discovers the file, detects format, infers column roles, engineers features, and writes partitioned Parquet + _schema.json to clean bucket. (5) Glue SUCCEEDED event triggers EventBridge Rule 2. (6) EventBridge invokes crawler-trigger Lambda which starts both crawlers. (7) After crawlers complete, Lambda anomaly detector is invoked manually. (8) Lambda reads _schema.json, builds dynamic features, trains Isolation Forest, scores data, writes scored Parquet + top_anomalies.csv + _summary.json, and sends SNS alert. Results are viewable via Athena, QuickSight, and the web portal.

### 3.15.2 Manual Pipeline Invocation Commands

**Screenshot:** Terminal showing the complete sequence of AWS CLI commands: `aws s3 cp train_transaction.csv s3://payflow-raw-transactions-dev-104573823385/`, `aws glue start-job-run --job-name payflow-etl-job`, `aws glue start-crawler --name payflow-clean-crawler`, `aws lambda invoke --function-name payflow-anomaly-detector`, `aws glue start-crawler --name payflow-scored-crawler`.

**Description:** While the pipeline auto-triggers via EventBridge on S3 upload, it can also be invoked manually for debugging. The sequence is: upload data → start Glue job → wait ~5 minutes → start clean crawler → wait ~1 minute → invoke anomaly Lambda → start scored crawler. The crawlers don't emit completion events, which is why Lambda must be invoked manually after crawlers finish. A Step Functions state machine could automate this in a production setting.
